# 数据源实测记录

每接入一个源都在这里留一行结论。**没跑通 `vpr crawl --dry-run` 的源不要进 `SEED_SOURCES`**：
`enabled = true` 意味着每天都会被请求，猜错一次就是每天骚扰人家一次。

抓取规则见 [`ARCHITECTURE.md`](ARCHITECTURE.md) §5；合规底线见 `AGENTS.md` 硬性规则 2。

### 列表入口为什么从翻页换成 sitemap（有赞）

`https://tech.youzan.com/` 的 HTML 列表能用，但翻页到 2022 年之前要 70+ 次请求，还得靠「越界页 404」判断到底。
`sitemap-posts.xml` 一次请求返回 **351 个文章 URL**（2026-10-31 实测，87 KB，带 `lastmod`），
回填与增量共用同一条路：增量时清单里的已知 URL 一次请求都不发，稳态仍是 1 次/天。

代价是列表层拿不到标题与时间——都由详情页补（`Detail.title`），列表只负责「发现新条目」。
管道对「列表只给 URL」的条目有一条快路径：库里已有正文就直接算未变，不发任何请求（`pipeline.ts`）。

> 美团做不到这一点：`/robots.txt`、`/sitemap.xml`、`/archives/`、`/page/2/` 全部 302 到 `/404.html`，
> 只有 RSS 这一个入口。**美团的历史文章拿不到**，库里只有最新 10 篇，这是已知上限。

### 实测数据（2026-10-31，本机）

```text
有赞首页 5 条/页，第 2 页 5 条，越界页码返回 404（这是「翻到底」的正常信号）
美团 feed 固定 10 条，最后一条之后没有翻页概念

batch #1  backfill --max-pages=1   meituan 10 插入（1 请求） + youzan 5 插入（6 请求，5.3s）
batch #2  incremental              meituan 10 未变（1 请求） + youzan 补 5 条（7 请求：2 页列表 + 5 详情）
batch #3/4 incremental            meituan 10 未变（1 请求） + youzan 10 未变（2 请求，1.2s）
batch #7  backfill --max-pages=0   youzan 349 条（339 新增 / 10 未变 / 2 失败），342 请求，343s
```

回填后：359 篇 / 418 标签 / 2015–2022 + 2026 共 9 个年份；库 3.2 MB，正文 gzip 2.7 MB。

- **幂等成立**：batch #3 与 #4 的 `inserted` / `updated` 都是 0。
- **请求预算**：稳定态下两家合计 2–3 次请求/天（美团 1 次 feed；有赞 1 次 sitemap + 新文章各 1 次详情）。
- **体量**：20 篇 → SQLite 612 KB（含 FTS），正文 gzip 212 KB，约 10 KB/篇。
- 两家都不是「304 友好」的源：美团认 `If-Modified-Since` 但返回 200；有赞对相同 ETag 也返回 200。
  真正省请求的是**元数据没变就不进详情页**（有赞稳定态只发 2 次请求）。

### 踩过的坑

| 现象                                                   | 原因与处理                                                                                                                             |
| :----------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------- |
| `Cannot convert argument to a ByteString`              | UA 里写了中文。HTTP header 必须 ASCII，UA 改成 `boguan/0.1 (+…; aggregator; honors robots.txt)`                                        |
| 有赞详情页正文解析出 0 字                              | `node-html-parser` 在这页丢掉了 `<main>` 之后的整段文档。换 cheerio，并且**解析不到正文就抛错**                                        |
| 有赞回填 351 篇要 342 次请求还是 700 次                | 拿 canonical URL（去掉结尾斜杠）去抓详情页会 301 回来，等于每篇多一次请求。抓取用列表给的原始 URL，canonical 只做身份（`pipeline.ts`） |
| sitemap 里混着活动页、招聘页                           | `技术活动 \| …（已结束）`、`团队介绍` 这类页面也在 sitemap 里，正文只有几十字。当前按失败跳过（2 条），是否整类排除见 ARCHITECTURE §13 |
| 有赞标签出现 `bigdata` / `da-shu-ju` / `big-data` 三个 | 源站标签云里英语与拼音写法并存。按中文名归并（`da-shu-ju`→大数据），英语写法进 `SEED_TAG_ALIASES` 人工补                               |
| 美团时间全是「前一天 16:00Z」                          | 正常：URL 里只有日期、没有时刻，按 `Asia/Shanghai` 当 00:00 解释 → UTC 前一天 16:00                                                    |
| 增量模式第一天就往前翻了几页历史                       | 阈值「连续 10 条」大于每页条数（5），永远达不到。改成「**整页都早于水位**就停」，与页大小无关                                          |

## 接入一个新源的清单

1. `curl` 一下 `/robots.txt`，确认目标路径没被 `Disallow`；
2. 写适配器（`scripts/crawler/adapters/*.ts`），声明 `capabilities`；
3. `vpr crawl --dry-run --source=<slug>`：看标题、时间（含源串）、摘要字数、标签、详情页正文长度；
4. 在 `SEED_SOURCES` 加一条，`vpr db:seed`；
5. `vpr crawl --mode=backfill --max-pages=1`：确认入库 → 再跑一次确认幂等（`inserted/updated` 为 0）；
6. `vpr db:check` 全绿后，再考虑 `--max-pages=0` 全量回填；
7. 把结论补进上面的表。
